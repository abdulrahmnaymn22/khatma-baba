# ختمة بابا

موقع عربي لإدارة ختمتين يوميًا من القرآن الكريم إهداءً لروح الوالد رحمه الله. يستخدم واجهة HTML/CSS/JavaScript الحالية، بينما تُحفظ البيانات المشتركة في PostgreSQL عبر Supabase كي يراها المشاركون من هواتفهم وحواسيبهم.

## المزايا

- واجهة عربية RTL متجاوبة، مع ختمتين مستقلتين و٣٠ جزءًا في كل ختمة.
- لوحة مشارك بسيطة تعرض إسناداته وتقدمه الشخصي وسجله فقط.
- دخول المشارك بالاسم ورقم سري من أربعة أرقام، مع جلسة Supabase Auth مستمرة على الجهاز.
- دخول إدارة منفصل بحساب Supabase مصرح له بدور `admin`؛ لا يوجد تسجيل ذاتي للمشاركين.
- يمكن للمشارك استخدام PIN نفسه على أكثر من جهاز؛ لكل جهاز جلسة موثّقة مرتبطة بالملف الثابت نفسه.
- الإدارة وحدها تنشئ المشاركين أو توقفهم أو تجدد PIN الخاص بهم.
- ملفات المشاركين والدورات الشخصية وسجل تاريخي للإسنادات والإكمالات.
- منع إكمال الجزء مرتين في الدورة نفسها، حتى بين الختمتين، بقيد وفحص داخل قاعدة البيانات.
- إسناد وإكمال ذريّان عبر دوال PostgreSQL، لمنع تضارب التحديثات المتزامنة من أجهزة مختلفة.
- تحديثات Supabase Realtime، مع تحديث احتياطي دوري كل ٣٠ ثانية.
- توزيع تلقائي ذري للأجزاء المتاحة بحسب طلبات المشاركين، وسجل قراءاتهم وإسناداتهم السابقة.
- ختمتان يوميتان مستقلتان لكل تاريخ بتوقيت `Africa/Cairo`، مع أرشفة الأيام السابقة وانتهاء الإسنادات غير المقروءة دون احتسابها في الدورة الشخصية.
- Row Level Security (RLS) على كل الجداول المكشوفة. عمليات الكتابة تمر عبر دوال تتحقق من الدور وملكية ملف المشارك.

## نموذج الأمان

- Supabase Auth يتولى جلسات المشاركين والإدارة. ينشئ المتصفح جلسة Auth مجهولة، ثم تتحقق دالة PostgreSQL من الاسم وPIN وتربط معرّف الجلسة بملف المشارك. يستمر JWT/refresh token وفق إعدادات Supabase؛ بعد مسح بيانات المتصفح يسجل المشارك دخوله مجددًا بالاسم وPIN.
- لا يخزن التطبيق كلمات مرور المشاركين. حساب الإدارة فقط يستخدم بريدًا وكلمة مرور في Supabase Auth.
- لا تحفظ قاعدة البيانات PIN خامًا: تحفظ bcrypt للتحقق وبصمة HMAC داخل مخطط خاص غير مكشوف عبر Data API. لا يستطيع المشارك أو المشرف قراءة PIN الحالي. يظهر الرقم للمشرف مرة واحدة عند إنشاء المشارك أو تجديده.
- قيد فريد على بصمة PIN يمنع تكرار الأرقام الفعالة. تُحد المحاولات إلى خمس لكل اسم خلال ١٥ دقيقة، مع رسالة فشل عامة لا تكشف وجود الاسم.
- قاعدة بيانات Supabase تنشئ صف `app_users` عند تسجيل مستخدم جديد، وتمنحه دور `participant` دون الوثوق بأي دور أو `participant_id` يرسله المتصفح.
- المستخدم يستطيع تعديل اسم العرض فقط. لا يستطيع تغيير دوره أو ربط ملف مشارك بنفسه.
- يستطيع المشارك قراءة ملفه وإسناداته ودوراته وإكمالاته وسجل نشاطه فقط. تعرض لوحة الإدارة جميع المشاركين والإسنادات. إكمال الجزء يمر عبر RPC تتحقق من حساب الجلسة وملكية الإسناد.
- الإدارة وحدها تستطيع ربط الحسابات بملفات المشاركين أو إنشاء/إلغاء الإسنادات وإدارة ملفات المشاركين. RLS مفعل على كل الجداول، وRPC تتحقق من دور الحساب داخل PostgreSQL.
- المفتاح الموجود في `js/supabase-config.js` مفتاح نشر عام فقط؛ لا تضع `service_role` أو مفاتيح سرية في الواجهة.

## مخطط قاعدة البيانات

- `participants`: ملفات المشاركين، نشاط الملف، وإجمالي الأجزاء المكتملة.
- `khatmas`: الختمتان، و`juz`: الأجزاء ١–٣٠، و`khatma_juz`: علاقة الأجزاء بكل ختمة.
- `reading_cycles`: دورة شخصية لكل مشارك؛ يحفظ كل صف رقم الدورة وحالتها وتوقيتها.
- `assignments`: الإسنادات التاريخية مع الختمة والجزء والمشارك والدورة والتاريخ والحالة.
- `daily_khatmas` و`daily_khatma_juz`: سجل ثابت للختمة الأولى والثانية لكل يوم، ولكل سجل أجزاؤه الثلاثون وحالته `open` أو `closed`.
- `assignment_requests`: سقف الأجزاء الذي يطلبه كل مشارك لكل ختمة في اليوم؛ لا يحذف النظام الطلبات السابقة.
- `completions`: إثبات الإكمال مع قيد فريد `(cycle_id, juz_number)` لمنع تكرار الجزء في الدورة.
- `app_users`: ربط مستخدم Supabase Auth بدور `participant` أو `admin` وبملف المشارك.
- `activity`: سجل دائم للإسناد والإكمال والإلغاء وتغيير الإسناد وإغلاق/بدء الدورة.
- `admin_audit_log`: سجل داخلي لإضافة المشارك وإيقافه وإعادة تفعيله وتجديد PIN؛ RLS يتيح قراءته للمشرف فقط.

تُطبق سياسات RLS في `202609290007_participant_data_scope.sql` على قراءات المشاركين والإسنادات، فتقصر حساب المشارك على ملفه وسجله، بينما تحتفظ حسابات الإدارة بالعرض الكامل.

كل مشارك يبدأ بدورة نشطة رقم ١. لا يرفع الإسناد التقدم؛ زر «تمت القراءة» يسجل الإكمال. عند اكتمال الأجزاء الثلاثين، تنهي معاملة قاعدة البيانات الدورة وتبدأ التالية، مع الإبقاء على سجل الدورات والأحداث السابقة.

تُحسب بداية اليوم من ساعة PostgreSQL بتوقيت `Africa/Cairo`. عند تحميل البيانات، تستدعي الواجهة `ensure_daily_khatmas`؛ تنشئ الدالة سجلي اليوم (واحدًا لكل ختمة) والأجزاء الثلاثين لكل منهما، وتغلق الأيام السابقة وتحول الإسنادات غير المكتملة إلى منتهية. يعمل ذلك أيضًا عند أول زيارة بعد منتصف الليل أو بعد عدة ساعات، ولا يعتمد على بقاء مؤقت في المتصفح مفتوحًا. قيد فريد على التاريخ ورقم الختمة يجعل التكرار آمنًا عند تزامن الزيارات. الختمتان اليومية منفصلتان عن رقم الدورة الشخصية.

يعمل التوزيع التلقائي داخل دالة PostgreSQL واحدة. طلب المشارك لكل ختمة/يوم هو سقف عدد أجزائه، والسقف الافتراضي ٣٠ إن لم يحدد طلبًا. يوزع النظام الجزء التالي على من لديه أقل نسبة من طلبه اليوم، ثم الأقل إسنادًا في الختمتين اليوم، ثم الأقل إسنادًا في التاريخ. لا يعيد التوزيع كتابة الإسنادات الموجودة، ولا يسجل إكمالًا؛ الإكمال لا يحدث إلا بزر «تمت القراءة». إذا لم تكفِ الطلبات المؤهلة، تبقى بقية الأجزاء متاحة.

## إعداد Supabase

1. أنشئ مشروع Supabase، ثم افتح **SQL Editor** وشغّل بالترتيب ملفات `supabase/migrations/202609290001_shared_khatma.sql` إلى `supabase/migrations/202609290010_realtime_sync.sql` مرة واحدة لكل منها.
2. من **Project Settings → API Keys** انسخ عنوان المشروع ومفتاح **Publishable** (أو `anon` القديم)، وضعهما في `js/supabase-config.js` بدل `YOUR_PROJECT_ID` و`YOUR_SUPABASE_PUBLISHABLE_KEY`.
3. لا تضع `service_role` أو مفتاح `secret` في ملفات الموقع؛ مفتاح النشر العام ظاهر في المتصفح عمدًا، وتعتمد الحماية على RLS وسياسات قاعدة البيانات.
4. من **Authentication → Sign In / Providers** فعّل **Anonymous Sign-Ins** للمشاركين، وفعّل **Email** لمشرفي النظام. اضبط عمر الجلسة وفق حاجتك، وأضف عنوان التشغيل المحلي وGitHub Pages إلى **URL Configuration**.
5. أنشئ حساب الإدارة الأول من لوحة **Authentication → Users** في Supabase (لا توجد استمارة إنشاء حساب في الموقع). بعد إنشائه، استخرج UUID ثم نفّذ مرة واحدة في SQL Editor:

```sql
insert into public.app_users(user_id, role, participant_id)
values ('AUTH_USER_UUID', 'admin', null)
on conflict (user_id) do update set role = 'admin', participant_id = null;
```

6. سجّل دخول المشرف من الموقع، ثم أضف المشاركين من قسم **المشاركون**. سيظهر PIN عشوائي من أربعة أرقام مرة واحدة؛ أوصله للمشارك بطريقة خاصة. لا ترسله في مجموعة عامة. يمكن إنشاء رقم بديل لاحقًا من بطاقة المشارك، وسيُلغى الرقم السابق فورًا.

### المزامنة الفورية

يشغّل الترحيل `202609290010_realtime_sync.sql` الجداول اللازمة إلى `supabase_realtime` إن لم تكن مضافة. تأكد من أن خدمة Realtime مفعلة للمشروع. تشترك الواجهة في قناة `khatma-shared-<auth-user-id>` لأحداث الإدراج والتحديث في `daily_khatmas` و`daily_khatma_juz` و`assignments` و`completions` و`reading_cycles` و`participants` و`activity` و`app_users` و`assignment_requests` و`admin_audit_log`. جدول `daily_khatma_juz` يرسل الحالة العامة لكل جزء فقط ولا يحتوي اسم القارئ أو معرّفه؛ لذلك يستطيع المشاركون رؤية التغير في حالة الجزء دون الاطلاع على تكليفات الآخرين.

تُستخدم مرشحات المشارك حيث ينطبق ذلك، وتبقى RLS هي حد الصلاحية الفعلي. لا تستمع الواجهة إلى أحداث الحذف؛ Supabase لا يطبق RLS على أحداث Postgres Changes من نوع DELETE. عند وصول حدث أو عودة الاتصال أو إظهار تبويب معلّق، تعيد الواجهة تحميل البيانات من PostgreSQL بدل الاعتماد على محتوى الحدث أو ذاكرة محلية. كما توجد مزامنة احتياطية كل ٣٠ ثانية أثناء ظهور الصفحة. تحقق من خطوات التحقق الحي في `supabase/tests/realtime_test_plan.md`.

لترقية مشرف إضافي، أنشئ حسابه في Supabase Auth ثم غيّر `role` يدويًا في SQL Editor بعد التحقق من هويته. لا توجد أداة في واجهة الويب لمنح دور `admin`، ولا يمكن للمستخدم تعيين هذا الدور من بيانات الجلسة. PIN وسيلة دخول عائلية بسيطة؛ تعامل معه كرمز سري، لكن لا تعتبره مصادقة عالية الضمان.

## اختبار تزامن الإسناد

يوجد اختبار تكاملي يشغّل طلبَي إسناد متزامنين للجزء نفسه والمشارك نفسه عبر الختمتين اليوميتين، باستخدام تاريخ قاعدة البيانات في القاهرة. استخدم قاعدة اختبار منفصلة ومشاركًا مخصصًا؛ يُسند الاختبار الجزء مرة واحدة ثم يلغي صف الاختبار المحدد فقط مع حفظ سجل الإلغاء. يمكن كذلك تمرير جزء مكتمل لاختبار رفضه:

```sh
export KHATMA_TEST_DATABASE_URL='postgresql://...'
export KHATMA_TEST_ADMIN_USER_ID='<admin-auth-uuid>'
export KHATMA_TEST_PARTICIPANT_ID='<dedicated-test-participant-uuid>'
export KHATMA_TEST_JUZ=29
export KHATMA_TEST_COMPLETED_JUZ=4
sh supabase/tests/concurrent_cycle_assignments.sh
```

يلزم أن يكون الجزء `29` غير مكتمل وغير مسند في الدورة الحالية، وأن يكون الجزء `4` مكتملًا فيها عند استخدام المثال. يحتاج الاختبار إلى `psql` وإلى اتصال قاعدة بيانات بصلاحية `SET ROLE authenticated`. لا تشغله على ملف مشارك حقيقي.

يوجد كذلك `supabase/tests/daily_khatma_lifecycle.sh` لاختبارات التكامل على قاعدة اختبار منفصلة. يتحقق من إنشاء السجلين اليوميين دون تكرار، وأرشفة يوم سابق وانتهاء إسناده غير المقروء، وعدم احتساب المنتهي في الدورة، واستمرار الإكمال والدورات والتوزيع بين الختمتين. يحتاج الاختبار إلى `psql` واتصال مالك قاعدة البيانات ومعرف حساب إدارة، ويُنشئ مشاركين بأسماء تبدأ بـ`daily-test-` ثم يتراجع عن بياناته؛ لا تشغله على قاعدة بيانات الإنتاج.

اختبار إعداد اشتراكات Realtime المحلي لا يحتاج Supabase:

```sh
node supabase/tests/realtime_subscriptions.test.mjs
```

ويغطي مرشحات المشارك والمشرف، عدم الاشتراك في أحداث الحذف، وعدم اشتراك المشارك في سجل الإدارة، ودمج دفعة الأحداث المكررة في مزامنة واحدة. للاختبار الحي متعدد الجلسات، اتبع `supabase/tests/realtime_test_plan.md`.

ويختبر `supabase/tests/participant_dashboard_security.sh` نطاق RLS وإكمال المشارك: يقرأ المشارك إسناده وحده، يستطيع إكماله، ولا يستطيع قراءة إسناد أو ملف مشارك آخر أو إكماله، كما يرفض الإكمال المكرر. يتطلب قاعدة اختبار، ومعرف حساب إدارة، وحساب Auth مشاركًا مخصصًا غير مرتبط بملف آخر؛ تُتراجع تغييرات الاختبار في نهاية المعاملة.

اختبارات PIN ولوحة الإدارة عبر Supabase HTTP موجودة في `supabase/tests/participant_pin_auth.mjs`. تستخدم تسجيلًا مجهولًا وجلسة مشرف مؤقتة، وتغطي بيانات الدخول الصحيحة والخاطئة، تعدد الأجهزة، استمرار الجلسة، عزل RLS، إكمال الإسناد، التوزيع التلقائي، منع تغيير الأيام المؤرشفة، تجديد PIN، التعطيل وإعادة التفعيل، وسجل الإجراءات الإدارية. شغّلها على مشروع اختبار فارغ فقط بعد ترقية حساب اختبار إلى admin:

```sh
KHATMA_TEST_SUPABASE_URL='https://<TEST_PROJECT>.supabase.co' \
KHATMA_TEST_PUBLISHABLE_KEY='<TEST_PUBLISHABLE_KEY>' \
KHATMA_TEST_ADMIN_ACCESS_TOKEN='<SHORT_LIVED_ADMIN_ACCESS_TOKEN>' \
node supabase/tests/participant_pin_auth.mjs
```

يضيف الاختبار مشاركين وإسنادات تجريبية، ثم يعطّل المشاركين عند التنظيف؛ لذلك لا تشغّله على بيانات حقيقية، ولا تضع القيم في ملفات المشروع أو سجل الأوامر المشترك. تسجل `admin_audit_log` إنشاء المشاركين وإيقافهم وإعادتهم وتجديد PIN، وهي متاحة للقراءة للمشرفين فقط.

## التشغيل محليًا

لا توجد حزم بناء مطلوبة. بعد إعداد Supabase شغّل خادم ملفات ثابتة في مجلد المشروع:

```sh
python3 -m http.server 8000
```

ثم افتح <http://localhost:8000>. أدخل الاسم وPIN الذي أعطته الإدارة. يدخل المشرف عبر زر **دخول الإدارة** بحساب Supabase الذي أُنشئ مسبقًا.

## النشر على GitHub Pages

المشروع ثابت ولا يحتاج إلى خادم تطبيق. بعد إعداد Supabase والقيم العامة في `js/supabase-config.js`، ادفع الملفات إلى مستودع GitHub. من **Settings → Pages** اختر الفرع `main` ومجلد الجذر `/`. أضف عنوان GitHub Pages إلى **Authentication → URL Configuration → Redirect URLs** عند إعداد روابط البريد أو الاستعادة مستقبلًا. لا يحتوي التطبيق على أسرار خلفية.

## البيانات القديمة وإعادة الضبط

النسخة السابقة كانت تحفظ بياناتها في `localStorage` باسم `khatma-baba:data` (أو المفتاح الأقدم `khatma-baba:data:v1`). بعد تجهيز قاعدة Supabase وحساب الإدارة، وقبل إضافة مشاركين جدد، سجّل دخول المشرف من المتصفح القديم واضغط «استيراد بيانات النسخة المحلية» في قسم المشاركين. ينقل الاستيراد المشاركين والدورات والإسنادات والسجل مرة واحدة إلى قاعدة البيانات، ويترك نسخة المتصفح القديمة دون حذف. ملفات المشاركين المستوردة لا تملك PIN بعد؛ افتح بطاقة كل مشارك واختر «إنشاء رقم سري جديد»، ثم سلّمه الرقم الجديد بطريقة خاصة. يجب إجراء الاستيراد من نفس المتصفح الذي يحتوي البيانات المحلية؛ إذا تعذر ذلك صدّر JSON يدويًا واحتفظ به، فالأداة لا ترفعه من ملف خارجي. لا تضغط الاستيراد بعد إنشاء مشاركين جدد؛ قاعدة البيانات ترفض الدمج كي لا تكرر الأسماء أو التاريخ.

إعادة ضبط بيانات الموقع المنشور تتطلب حذف الصفوف من جداول Supabase عبر SQL Editor. احذف سجلات `activity` و`completions` و`assignments` ثم `daily_khatma_juz` و`daily_khatmas` و`assignment_requests` و`reading_cycles` ثم `participants`؛ اترك جداول `khatmas` و`juz` و`khatma_juz` كما هي. يمكن حذف جلسة الدخول من زر «خروج» أو من إعدادات المتصفح، لكن ذلك لا يحذف البيانات المشتركة.

## إنشاء مستودع GitHub ودفعه

أنشئ مستودعًا فارغًا على GitHub، ثم من مجلد المشروع نفّذ الأوامر التالية مع استبدال القيم بين `< >`:

```sh
git init -b main
git add index.html css/styles.css js/data.js js/auth.js js/app.js js/history.js js/supabase-config.js README.md supabase
git commit -m "Connect Khatma Baba to Supabase"
git remote add origin https://github.com/<GITHUB_USERNAME>/<REPOSITORY_NAME>.git
git remote -v
git push -u origin main
```

استخدم مدير بيانات اعتماد GitHub أو `gh auth login` لتسجيل الدخول. لا تضع رموز الوصول أو كلمات المرور في عنوان `remote` أو ملفات المستودع.
